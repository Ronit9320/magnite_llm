## Things testers will notice

- **First GPU chat after install pauses ~10 s, once per macOS user.** The Metal shaders compile and are then cached (ISSUE-002). Every
  later load measured 0.01–0.05 s for the shader library and ~1 s for a whole model.
- **Memory.** Peak RSS stayed ≤ 2.1 GB for every cell; the 1.5B GGUF on CPU was the largest. A 1.5B Q4 model fits an 8 GB Mac
  comfortably. Larger models were not measured.
- **torch MPS start-up** costs ~9 s on the first load in a process (`torch-mps-infer` `load_s`), against ~2.5 s on CPU.

## Performance notes (not claims)

- On a base M1, llama.cpp decode for a 1.5B Q4_K_M model runs about the same on CPU and GPU: 49.3 tok/s CPU, 46.0 at the app's
  20 layers, 43.8 with all layers. Full offload loads fastest (0.3 s) and uses the least memory (1.3 GB vs 2.1 GB CPU).
  On the 135M model the CPU is ~3× faster than Metal, because tiny models are dominated by dispatch overhead. **No measured reason to
  change `n_gpu_layers`.** Prompt prefill, larger models and Pro/Max GPUs were not measured, and that is where Metal usually wins.
- Single runs of 128 tokens are noisy. The table reports the median of 5 (llama.cpp) or 3 (torch) runs after a warm-up, with the
  observed range.

## Limits of this measurement

One machine (M1, 8 GB, macOS 27.0.1); models ≤ 1.5B parameters; 12-step training runs. These prove each path *works*; they do not
measure fine-tuning quality. macOS 14.x/15.x were not run (ADR 0002). Training cells use the backend's `run_training` directly. The
UI/HTTP path is covered by the app selftests, which pass 11/11 since the ISSUE-010 fix.
