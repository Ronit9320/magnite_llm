## Work remaining against BUILD_PLAN.md

### Earlier phases marked complete

- **Phase 0:** `shared/` remains empty. Contracts exist as routes, Pydantic schemas and C++ request builders; there is no shared, separately maintained/generated IPC contract.
- **Phase 3:** Apple Silicon/Metal/MPS detection and selection are missing. Windows GPU detection explicitly returns unsupported. GPU allocation is hardcoded. Global Settings engine override is not wired to inference. Registered-model resolution is broken (F2). The API supports OpenAI-like inputs, but custom SSE output and no non-streaming response (F11) fall short of full compatibility. GGUF conversion/format-aware engine selection is absent; an HF training model is not automatically a llama.cpp-compatible model.
- **Phase 4:** Training jobs/history are memory-only, and each submitted job starts a daemon thread immediately; there is no serialized resource-aware queue. Job history disappears on backend restart. Local dataset ingestion and training work; restart recovery and a durable history UI remain incomplete.
- **Phase 5:** Adapter activation always unloads/reloads a PEFT/torch engine. Native vLLM multi-LoRA hot-swapping and llama.cpp GGUF-adapter restart integration are not implemented. Clearing an adapter unloads inference rather than restoring the plain base model. Filtering adapters by base model is absent; the list API only filters names. Export/import exist but need correctness and safety fixes.

### Phase 6: implemented substantially, documentation stale

Working code exists for PDF/TXT/Markdown/HTML extraction, word-based chunking, sentence-transformer embeddings, persisted vectors, top-k/threshold query APIs, config APIs, document management, a RAG panel, a Chat toggle, and context injection.

Remaining gaps/deviations:

- Vectors use SQLite blobs plus a NumPy full scan, **not ChromaDB or FAISS** as specified. This is an implementation deviation, not evidence that small-store retrieval fails.
- Similarity threshold is API-only. The UI exposes chunk size, overlap and top-k; it does not offer per-chat top-k/threshold overrides or embedding-model selection. RAG toggle is in Chat rather than the RAG panel.
- No ingestion job API with progress/cancellation; one synchronous HTTP request performs each embedding operation.
- No model-change reindex workflow, context-window/token-budget management, or visible retrieval-failure reporting. These are reliability needs exposed by the implementation, beyond the plan's minimal feature list.
- Chunk sizes are whitespace-word counts, despite being labelled tokens. Markdown extraction removes code blocks and inline code, which limits retrieval over technical documents.
- Configuration validation and preservation need fixes (F8/F9).

## Defects and evidence

### F1 — High: adapter ZIP imports can write outside their destination (reproduced)

`backend/src/backend/routes/adapters.py:117` joins archive member names directly to the destination. A harmless archive containing `weights/../escaped.txt` returned HTTP 201 and wrote into the parent directory. Absolute paths and deeper traversal are also unchecked. Archive-supplied IDs are insufficiently validated (`..` remains possible), and imported directories are later recursively deleted.

Fix: validate IDs; resolve every extraction destination and require it to be strictly inside a fresh adapter directory; reject directory/symlink/path-traversal surprises; validate weights before registering; clean up failed imports.

### F2 — High: loading a model selected from the registry is broken (code path and validation reproduced)

`app/src/panels/chatpanel.cpp:271` populates the selector with IDs such as `huggingface:owner--model`; `onLoadModel` sends that string unchanged. `InferenceSupervisor.load_model` and `LlamaCppEngine._resolve_gguf_path` do not resolve registry IDs. HF rejects the string with `HFValidationError`. Library Load uses the same path. Ollama records likewise have no inference bridge to an actual GGUF file or Ollama chat API.

The passing inference selftest uses a raw GGUF repository name and therefore misses this user workflow. Resolve the record to its source/ref/local files, and select a compatible engine before loading.

### F3 — High: runtime settings save but have no effect (code-confirmed)

`app/src/panels/settingspanel.cpp:134` reads/writes `engine/override`, `storage/dataDir`, `hosted/endpoint`, and `hosted/apiKey`. No runtime consumer reads these keys. `BackendManager` inherits environment variables and launches with `--port 0`, not the saved data directory. The separate Chat engine selector does work. Hosted keys are also stored as ordinary QSettings values, despite password masking in the UI.

### F4 — High: adapter inference is buffered until generation completes (reproduced with controlled model)

`backend/src/backend/inference/engines/torch.py:97` finishes `model.generate()` before iterating its streamer. Probe event order: generation starts → generation ends → streamer read → first queued token. Multiple SSE deltas therefore do not prove live streaming. This code also writes to an `asyncio.Queue` from a worker thread without a thread-safe event-loop bridge; cancellation does not stop the generation worker.

### F5 — High: inference failures can disappear from the UI (code-confirmed; vLLM suppression reproduced)

`app/src/panels/chatpanel.cpp:424` handles only `delta` and `done`, ignoring the backend's `{error: ...}` SSE event. HTTP 200 with an error event is not reported as a generation error. The `statusCode == 0` early return also treats network failure like intentional cancellation and can leave streaming controls stuck.

`backend/src/backend/inference/engines/vllm.py:90` and `:120` suppress every exception. A simulated upstream failure returned an empty stream rather than an error, which the route can finish with `done: true`.

### F6 — Medium: Ollama deletion is undone on refresh (reproduced with mocked Ollama listing)

`backend/src/backend/models/registry.py:278` deletes only the registry entry for Ollama. The next `list_synced` imports it again from Ollama. The probe returned one model immediately after deletion. Implement Ollama deletion or an explicit persistent hide/unregister behavior.

### F7 — Medium: HF deletion does not reclaim the weight blobs (reproduced with synthetic HF cache layout)

`backend/src/backend/models/registry.py:168` removes only the revision snapshot directory. HF snapshots link to blobs elsewhere; the blob survived the deletion probe. Use cache-aware revision deletion that accounts for shared files.

### F8 — Medium: invalid RAG chunk configuration is accepted (reproduced)

`backend/src/backend/rag/schemas.py:8` does not require overlap < size; `/rag/config` accepted size 64, overlap 1024 with HTTP 200. Per-ingest size/overlap have no bounds: negative size -1 returned HTTP 201 while silently discarding content in the probe. Excessive overlap reduces the stride to one word, inflating embedding work and duplicate chunks.

### F9 — Medium: changing visible RAG settings resets hidden settings (reproduced)

`app/src/panels/ragpanel.cpp:390` sends only chunk size, overlap and top-k. The endpoint replaces the entire `RagConfig`, defaulting `min_score` and `model`. Setting threshold 0.8/custom model then submitting the UI-shaped body reset them to 0/all-MiniLM-L6-v2. Existing documents can then disappear from retrieval because search filters by embedding model. The UI also ignores config-save errors.

### F10 — Medium: malformed requests/imports return internal errors (reproduced)

`POST /inference/load` with `{"model":123}` returns HTTP 500 because `.strip()` is called before validation. Adapter ZIP with `record.json={}` also returns HTTP 500 from uncaught Pydantic validation. An archive with metadata alone can be registered as ready without usable weights. Use typed requests and explicit archive/content validation with appropriate 4xx responses.

### F11 — Medium: unsupported engine and non-streaming requests are silently mishandled (reproduced)

`InferenceSupervisor.make_engine('torch', ...)` returns `LlamaCppEngine`; every engine name except `vllm` falls through to llama.cpp. `/inference/chat` with `stream:false` still returns SSE. Validate supported engine names and implement or explicitly reject unsupported response modes.

### F12 — Medium: common instruction datasets silently lose their target answer (reproduced)

`backend/src/backend/training/datasets.py:184` accepts an instruction/input/output record but keeps only the first matching field (`input` before `instruction`) and drops `output`. Probe input `{instruction:'Say hello', input:'to Alice', output:'Hello Alice'}` normalized to `{text:'to Alice'}`. Malformed JSONL rows are also silently skipped. This schema is not explicitly promised, but accepting it as usable training data without reporting loss is misleading. Support known schemas or reject unsupported rows visibly.

### F13 — Medium: lifecycle/concurrency/cancellation remain unsafe (code-review risks, not destructive runtime tests)

- Supervisor load/unload/adapter operations have no shared lifecycle lock against concurrent generation or loads.
- vLLM uses fixed port 8001, synchronous HTTP inside async streams, suppresses errors, and discards subprocess logs. No shutdown hook unloads the engine; a subprocess whose startup times out is not cleaned up by `load_model`.
- llama.cpp generation executes synchronous token iteration in the async request path; responsiveness under real-model load is unverified.
- Qt non-streaming requests time out after 60 seconds, while vLLM startup alone can wait 240 seconds and downloads/embedding may take longer. A UI timeout does not cancel the backend work.
- Training starts every job immediately on a daemon thread, permitting GPU resource contention. No durable recovery exists.

### F14 — Medium: RAG can fail silently or exceed inference context (code-confirmed risks)

`backend/src/backend/rag/context.py:9` catches embedding/retrieval failures and returns no context without notifying the user. The route prepends all retrieved text without a token budget; the llama.cpp context defaults to 2048 while retrieval defaults to four 512-word chunks, before adding conversation history. Large-document RAG chat was not tested end-to-end.

### F15 — Medium: basic selftest can pass with a dead backend (reproduced)

The sandbox prevented backend startup, but the bare selftest printed `backend not ready, skipping IPC check` followed by PASS. Feature flags correctly wait/fail. Keep a distinct UI-only result or make the basic integration check fail when startup fails. The RAG cleanup assertion also allows a failed document-list request to count as successful cleanup (`mainwindow.cpp:1079`).

### F16 — Documentation/spec drift (confirmed)

- README calls RAG a placeholder, although its integration test passes.
- README swaps hosted/cloud phase numbers relative to BUILD_PLAN.
- BUILD_PLAN/design_doc describe blue-on-black space UI, while the current implementation/screenshots use orange-accent Studio light/dark themes. The theme selfcheck validates current code, not adherence to the old design document. Reconcile the intended specification rather than blindly reverting the UI.
- Claims of prior verification are not substitutes for missing coverage: tests count deltas but do not test first-token latency, failure visibility, registry selection, or full RAG conversations.

## Scope limits and suggested order

No live vLLM service, live Ollama server, Apple/Windows hardware, large-model/OOM scenarios, PDF corpus, or full RAG+adapter conversation was verified. Ollama deletion and vLLM error tests used controlled stubs; HF cache deletion used a temporary synthetic cache. ZIP tests wrote harmless markers only inside the audit temporary tree.

Prioritize F1, F2, F3 and F5; repair streaming/cancellation and storage deletion next; add regression coverage for the reproduced failures; then finish hosted inference and the remaining roadmap. RAG should be recorded as substantially implemented with explicit remaining gaps, not restarted as an absent feature.

## Remaining scope and limits

- No reproduced failure remains in the checks above. This is evidence for these flows, not a guarantee that the entire application is bug-free.
- Live vLLM and live Ollama behavior, large-model/OOM workloads, macOS/Windows hardware, and forced-process-death behavior across all engine subprocesses remain unverified. External-service failure/deletion regressions use controlled mocks. HF reclamation tests use synthetic caches so shared real weights are not deleted.
- Cancellation waits for a native model-loading, embedding or generation call to yield/return. vLLM startup checks cancellation during its readiness loop. Progress UI and independently managed ingestion/download jobs remain roadmap work.
- RAG token budgeting uses the loaded tokenizer where available and conservative message-overhead estimates for other engines. Very unusual model-specific chat templates still need broader coverage. The tiny model's output was checked for successful delivery, not factual quality.
- Hosted inference, cloud training, native vLLM multi-LoRA/llama.cpp adapter workflows, broad UX persistence, CI and distributable packages remain outside this defect-fix scope. Disabled hosted controls do not represent an implemented hosted engine.
- `BUILD_PLAN.md` and `design_doc.md` remain gitignored local documents; the portable status and test instructions are in README/AGENTS and this audit. All changes are on `dev`; this task did not create a commit or publish anything.
