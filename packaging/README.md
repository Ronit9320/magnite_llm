# Test packaging

`release/v0.1-testing` is the work branch for unfinished v0.1 packages. These
scripts do not publish releases, push branches or modify the developer venv.

## Linux x86-64

Install CMake, a C++20 compiler, Qt6 Widgets/Network/Svg development files,
`curl`, and `uv`. Then run:

```sh
bash packaging/build_appimage.sh
```

Artifacts go to `dist/`; staging, logs and tools stay under `build/packaging/`.
The first build downloads a standalone Python 3.12.12 runtime and CPU ML
dependencies, builds portable CPU llama.cpp, then uses linuxdeploy and its Qt
plugin to assemble the AppImage. No developer virtualenv or model caches are
copied. The runtime is installed as a normal backend wheel, not an editable one.
Build tools currently come from their continuous channel; this is a testing
recipe, not a fully locked public release pipeline.

Python dependency versions are recorded under `usr/bin/build-info/` inside the
image. Project/font/Qt notices and installed Python license metadata accompany
the package. Build on the oldest Linux distribution you intend to support;
glibc is provided by the host, not bundled by AppImage.

The desktop binary checks for `runtime/` next to itself. When present it starts
that runtime's Python in isolated mode, with no fallback to a system interpreter.
Without that directory the existing development layout still works.

Use `packaging/TESTING.md` for tester instructions. Windows packaging is a
separate follow-up; no Windows artifact is generated by this script.

Verify a relocated package, using disposable application data:

```sh
python3 packaging/smoke_appimage.py dist/Magnite-0.1.0-test.1-x86_64.AppImage \
  --logs build/packaging/relocated-tests --cache build/packaging/test-cache --features
```

This requires loopback access and downloads small test models. It checks the
theme, UI, desktop/backend startup, GGUF inference, and the combined CPU
LoRA/adapter/RAG workflow. It deliberately supplies broken host Python paths
and runs an extracted copy from a temporary location outside the checkout.

## macOS Apple silicon (arm64)

The macOS recipe lives in [`macos/`](macos/README.md). It needs Command Line Tools, CMake, `uv` and the pinned official Qt 6.8.3
(`MAGNITE_QT_ROOT`), then:

```sh
bash packaging/macos/build_app.sh     # Qt + isolated Python 3.12 runtime + backend -> ad-hoc signed Magnite.app, verify_bundle.py gate
bash packaging/macos/build_dmg.sh     # -> dist/Magnite-0.1.0-test.1-arm64.dmg and dist/SHA256SUMS-macos
bash packaging/macos/check_dmg.sh dist/Magnite-0.1.0-test.1-arm64.dmg
bash packaging/macos/verify_installed.sh <app> <log-dir> <hf-cache>   # full acceptance set on an installed copy
```

The runtime is installed from `macos/requirements-macos-arm64.txt` under the full lock `macos/constraints-macos-arm64.txt`.
llama-cpp-python is built from source with Metal; bitsandbytes is not included. The client launches the bundled interpreter with `-I -B`
and never falls back to a system Python once `Contents/Resources/runtime` exists. Regressions run through
`bash packaging/macos/run_regressions.sh` (a bare `unittest` run is affected by the `/var` symlink).

These are **testing** builds: ad-hoc signed, not notarized, one architecture, minimum macOS 14.0. Developer ID signing and notarization
are not done (blocked on a certificate). Tester instructions: [`macos/TESTING.md`](macos/TESTING.md). Evidence and limits:
[`docs/release/macos/V0_1_MACOS_TESTING.md`](../docs/release/macos/V0_1_MACOS_TESTING.md).
